## 2. 기각·부분 판정 상세

**B5 (기각).** B 는 "RearSlam 은 내리찍는 자세가 13프레임에 끝나 17프레임까지 멈춰 있고 16프레임에 맞는다"를 rig_dino.py `slam_keys` 로 댔다. 그러나 `slam_keys`(309행)는 첫 판 `Attack_Slam` 이고, 게임의 `Attack_RearSlam` 은 `rear_slam_keys`(427-445행, ACTIONS 540행)다. 여기서는 16프레임이 내리찍기 키이자 맞는 순간(=(16−1)/30 = 0.50 s, player.gd:31)이고, 18프레임 `quake`(목·꼬리가 늦게 출렁)·21프레임 `settle`·34프레임 원위치가 따로 있다. 네 변형 모두 quake·settle 키가 있다(437-438·457-458·476-477행). 그래서 "출렁이 어느 칸에도 없다"는 데이터와 다르고, 시트 간격(0.13~0.18 s)으로는 2프레임짜리 출렁을 못 잡는다. "두 칸 안에 처음 자세로 돌아온다"도 LowCharge 시트에서 맞는 칸(0.33 s) 뒤 0.82 s 까지 네 칸에 걸쳐 돌아온다. 남는 사실은 "출렁·여운이 작다(6~16°)"와 "찌그러짐이 없다" 정도. 덧붙여 `Attack_Slam`·`slam_keys` 는 게임이 쓰지 않는 동작이다(ATTACKS 에 없음).

**A2 (부분).** design.md:14 "로우폴리 + 단색 면 + 약한 명암"은 정확히 인용됐고 화면이 그대로다. 그러나 '시푸 화면 수준'이라는 시각 목표는 저장소 문서 어디에도 없다(grep '시푸': 손맛·콤보 레퍼런스뿐, motion.md:73 GDC 강연 링크만). 또 시푸도 각진 형태를 쓰므로 '로우폴리' 자체는 반대가 아니고, 어긋나는 것은 '단색 면·약한 명암' 부분이다.

**A3 (부분).** still_home_3 에서 등·머리가 어두운 문 구멍과 겹쳐 묻히는 것은 맞다. still_home_2 는 Ram 이 화면 높이 약 1/3 이고 몸이 바닥보다 확실히 어둡다. still_home_5 도 다리·꼬리 윤곽이 바닥 위로 읽힌다 — "흰 돌머리만 보인다"는 과장. 몸이 남색으로 보이는 것은 몸색(차콜 0.22, design.md:147)이 아니라 집 안 푸른 보조광(commute.gd:463-464) 탓이다.

**A1 하위 주장(기각).** "회사 건물도 옆 건물과 높이가 비슷해 주인공 건물로 서지 않는다": 회사는 9층 18.6 m + 시계탑(build_commute.py:266-269·303-306), 가까운 옆 건물은 9.5·12.5 m(316행). 화면 가운데에 놓이고 불 켜진 창·시계가 있어 still_road_5·zoomout 8칸에서 시선이 간다. 색이 같은 회색이라는 점만 맞다.

**A8 하위 주장(기각).** "회색 안개가 하늘·건물·바닥 색을 다 뺀다": `fog_sky_affect = 0.0`(commute.gd:434)이라 하늘은 안개를 안 받고, still_road_5 하늘은 파랗다. 건물이 회색인 것은 재질이 회색 콘크리트(M_CONC 0.60·0.62·0.65, build_commute.py:120)이기 때문이다. 안개(0.006)를 고쳐도 회색 도시는 그대로다.

**B7·C7 (부분).** 시트 칸은 1280×720 을 640×360 으로 줄인 것(make_sheets.py:27·33)이라 "십여 픽셀"은 시트 기준이다. 원본 4.17 s 컷에서 Ram 은 약 28 px. 3.9% 는 도착해 `input_enabled=false` 가 된 순간 값이다. 줌 아웃·하늘까지 보이는 정문 구도는 사용자가 승인한 연출이다(handoff.md:23). 다만 조작 중에도 4~6% 이고 그 구간에 직원 둘이 막고 있어(commute.gd:57) 조작 문제로는 유효하다.

**C8 (부분).** 집 오른쪽 벽 58°·왼쪽 56° 를 그대로 재현했다(verify_skeptic.gd). 그런데 C 가 내놓은 해법(위 방향을 매 프레임 카메라 방향으로 계산)으로 바꿔 재면 33°·30° 가 남는다. 길도 30° → 18°. 남는 몫은 화면 가장자리의 원근 수렴이라 고정 카메라에서는 피할 수 없고, 따라가는 길 카메라에서는 '정지 화면 한 걸음' 기준 자체가 체감과 다르다. "똑바른 키가 늘 20° 안" 조건은 C 의 해법으로 닿지 않는다. 장면마다 같은 키가 다른 동작을 하는 지적(아래+Space 등)은 그대로 확인.

**B8 (부분).** close_* 여섯 장은 별도 카메라(시야 40°, Ram 둘레 1.3~3.4 m)다(audit_capture.gd:26-28·40-57). close_road_4_top 은 거의 수직 위라 게임 어디에도 없는 각도라 "게임에서 가장 오래 보는 각도"의 근거가 될 수 없다. 게임 등 뒤 카메라(seq_road_Dash·RearSlam 1칸)에서는 돔 윗부분이 실루엣 위로 보인다. 찡그린 눈매는 사용자가 확정한 반달 눈(design.md:125, eye_approved.png)이므로 결함이 아니라 취향 문제다.

**B6 (부분).** seq_home_hatch 9칸(1.9 s)에서 눈이 보이고, 10칸에서 옆얼굴 전체가 보인다. 11~13칸 앞쪽 흰 조각은 2.5 s 뒤 줄어 사라진다(commute.gd:43·325-327). 7·8칸이 가려지는 것과 정점이 HUD 줄에 붙는 것만 맞다.

**B10 (부분).** verify_root_lift.gd: 게임 안 골반이 백스텝 0.10 m, 대시 0.05 m, RearSlam 0.14 m 올라간다. 공중이 없는 것이 아니라 작다. 시트는 매 칸 Ram 둘레로 잘라 맞추므로(audit_capture.gd:135-138) 높이 변화를 볼 수 없다.

**C2·C9 (부분).** 박치기 4종 번갈아 쓰기(design.md:163)와 0.35 s 길게 누르기 피니시(design.md:164)는 사용자가 정한 것이다. 겉모습 변주가 발생 시점·사거리까지 바꾼 부작용, 그리고 헛쳐도 콤보가 이어지는 것(설계 문구 "맞은 뒤"와 다름)은 유효하다.

**D3 (부분).** 미커밋·미푸시, `free_move` 가 수정본에만 있다는 것은 맞다. "9일 동안 한 작업"은 마지막 커밋(11/11) 뒤 지난 날수일 뿐이다. 저장소 안 새 파일 12개는 모두 11/20 15:25~16:03 에 생겼고 시안 폴더 home 은 11/17, commute 는 11/20 이다. 위험은 실제지만 규모는 '이틀치 작업'에 가깝다.

**D4·D2 (부분).** D4 의 사실(설계 문서에 '출근길' 없음, 조작은 방향키 10.5 s)은 맞다. 그러나 집 장면은 설계의 거점이고 design.md:95 의 '집 → 로비 도착'을 화면으로 옮긴 것이다. 사용자 승인도 기록돼 있다. 우선순위 비판으로는 D1 과 같은 말이다. D2 도 시험용 방 하나에 '한 판 5분'을 대어 본 것이라 D1(층·적이 없음)과 겹친다.

**D10 (부분).** design.md:179·184 가 이미 '원작 명칭 패러디, 출시 전 상표 검토 필요'라고 적었다. design.md:63 의 '사이버펑크 2077 용어 금지'는 인간성 게이지 문단에 붙은 말이다. "한 글자 차이"는 사실과 다르다.

**따로 기각된 하위 주장 7개:** A1 '회사 건물이 서지 않음', A8 '안개가 하늘까지 탈색', A10 'still_road_5 Ram 아주 작음', B2 '대시 최고 약 4 m/s', B8 'top 각도가 게임 각도', B5 전체, D10 '한 글자 차이'.

## 4. 바뀌어야 할 점수

- **B 연출: 1 → 2가 맞다.** 근거 둘이 과장됐다. 알 깨기 정점·착지 직전 얼굴이 보이고(hatch 9·10칸), 줌 아웃은 승인된 연출에 원본에서 Ram 이 보인다.
- **B 동작의 맛: 1 유지는 가능하다.** 다만 근거 가운데 '여운·출렁 없음', 'RearSlam 은 멈춘 뒤 맞음'은 빼야 한다(B5 기각). 남는 근거는 찌그러짐 없음, 출렁이 작음, 키 5~7개짜리 블로킹 수준.
- **D 독창성·권리: 1 → 2가 맞다.** 위험 요소 하나(산재비스탄)는 이미 문서가 알고 있는 출시 전 확인 항목이다. D 스스로 조력자 말장난과 세계관은 고유하다고 했다.
- **D 작업 위험: 1 유지.** 근거 문구는 '9일치'를 '11/17·11/20 이틀치 작업'으로 고쳐야 한다.
- **A 집 구도: 1 유지.** 근거 'Ram 이 작다'는 빼고 '흰 알이 시선을 가져간다'만 남긴다.
- **A 시험용 층 열**: 점수는 사실이지만 화면별 '가장 나쁜 화면' 선정과 합계 비교에서 빼야 한다(시험용 회색 방).

## 5. 평가자가 놓친 것

1. **집 안이 밖보다 크다.** 바깥 Ram 집 이글루 반지름 3.0 m(build_commute.py:239 `HOME = (-6.2, 7.0, 3.0)`), 안쪽 방 모델 반지름 4.0 m(build_home.py:25 `R = 4.0`). 현관을 나서는 순간 화면이 바뀌니 바로 드러나지는 않지만, 안팎이 같은 물체가 아니라는 A4 의 인상을 크기에서도 뒷받침한다. D5 의 '방 벽 숫자 셋(2.85·3.4·4.0)'에 바깥 3.0 이 하나 더 있다.
2. **게임이 쓰지 않는 동작 `Attack_Slam` 이 GLB 와 rig_dino.py 에 남아 있다.** ATTACKS(player.gd:30-39)에도 COMBO_LINKS 에도 없다. `slam_keys` 와 `rear_slam_keys` 이름이 비슷해 평가자 B 가 실제로 잘못 읽었다(B5). 쓰지 않는 데이터가 오독을 부른 사례다.
3. **C8 의 해법으로는 집 방향 어긋남이 절반만 준다.** 매 프레임 카메라 기준으로 바꿔도 33° 가 남는다(직접 잼). 고정 카메라 방에서 '위 = 화면 위'를 원하면 카메라를 더 멀리·좁은 화각으로 두거나, Ram 의 화면 위치 기준 방향을 써야 한다. 평가대로 고치면 기대만큼 안 나아진다.
4. **출근길 회색은 안개가 아니라 재질 문제다.** A8 을 따라 안개를 손대도 화면은 거의 안 바뀐다. 건물 재질(M_CONC·M_CONC2)이 거의 무채색 회색이고, 게임 내보내기에서는 얼룩도 사라진다(build_commute.py:54-55). 손댈 곳은 재질 색이다.

검증 스크립트: `measure/verify_skeptic.gd`, `measure/verify_root_lift.gd`(둘 다 헤드리스, 프레임 상한, quit). 저장소 파일은 고치지 않았다.
